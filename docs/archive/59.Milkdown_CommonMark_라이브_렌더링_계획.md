# Milkdown CommonMark 라이브 렌더링 계획

## 배경/문제
- 스레드/댓글/답글 작성 시 렌더 결과를 즉시 확인하기 어렵다.
- 작성 후 결과 확인을 위해 저장/등록이 필요해 입력 흐름이 끊긴다.
- WYSIWYG 수준의 라이브 렌더링을 제공하지 않아 편집 경험이 제한된다.

## 목표
- 스레드/댓글/답글 작성 화면에서 라이브 렌더링을 제공한다.
- 편집기는 Milkdown + CommonMark 플러그인 기반의 WYSIWYG으로 전환한다.
- 저장 포맷은 마크다운 문자열로 유지한다(HTML 저장 미사용).
- threads, entries에 `is_markdown` 필드를 추가하고 신규 작성 데이터는 `true`로 고정한다.

## 범위
- 포함 범위
  - 신규 스레드 작성(NewThreadComposer)과 스레드 편집(ThreadEditor)에 Milkdown 에디터 적용.
  - 댓글 작성(EntryComposer)과 답글 작성(ReplyComposer)에 Milkdown 에디터 적용.
  - 댓글 편집(EntryEditor)에도 동일 에디터 적용 여부 검토 및 반영.
  - Milkdown 공통 래퍼/훅/스타일 토큰 추가.
  - 백엔드에서 threads, entries에 `is_markdown` 필드 추가 및 API 응답에 포함.
  - 신규 작성/수정 시 `is_markdown=true`를 서버에서 강제 설정.
  - 기존 데이터는 `is_markdown=false`로 마이그레이션.
- 제외 범위
  - 서버 저장 포맷/스키마 변경 없음(마크다운 유지).
  - 기존 게시물 렌더링 로직 전면 교체는 제외(필요 시 단계적 전환).

## 현재 동작 정리
- 입력은 공통 `ComposerTextarea` 기반으로 구성된다.
  - 신규 스레드: `frontend/src/components/home/NewThreadComposer.tsx`
  - 스레드 편집: `frontend/src/components/home/ThreadEditor.tsx`
  - 댓글 작성: `frontend/src/components/home/EntryComposer.tsx`
  - 답글 작성: `frontend/src/components/home/ReplyComposer.tsx`
  - 댓글 편집: `frontend/src/components/home/EntryEditor.tsx`
- 본문/댓글 표시 영역은 텍스트 출력 및 검색 하이라이트 중심이다.
  - 스레드 본문 표시: `frontend/src/components/home/ThreadBodyDisplay.tsx`
- 백엔드는 threads, entries에 마크다운 여부를 구분하는 필드가 없다.

## 개선 방향
- 입력 영역을 Milkdown 에디터로 전환한다.
- CommonMark 문법 범위를 기본으로 하고, 확장 문법은 최소화한다.
- 마크다운 저장을 유지하므로 직렬화/역직렬화 품질을 최우선으로 한다.
- XSS 안전성 확보를 위해 렌더링 단계의 sanitize 정책을 명확히 한다.
- `is_markdown`은 사용자 입력과 무관하게 서버가 고정 값으로 설정한다.
- thread/entry 표시 시 `is_markdown=true` 데이터는 마크다운 렌더링으로 출력한다.

## 단계별 계획
- Phase 1: 요구사항 정리 및 에디터 스펙 확정
  - CommonMark 범위 확정 및 확장 문법 적용 여부 결정.
  - 링크/이미지 허용 정책과 보안 정책 수립.
  - 완료 기준: 에디터 스펙/보안 정책 문서화.

- Phase 2: Milkdown 공통 래퍼 도입
  - Milkdown core + commonmark 플러그인 구성.
  - 마크다운 직렬화/역직렬화 유틸 구성.
  - 완료 기준: 샘플 텍스트를 입력/저장/복원 가능.

- Phase 3: 스레드 작성/편집 화면 적용
  - `NewThreadComposer`와 `ThreadEditor`에 Milkdown 적용.
  - 기존 입력 이벤트/디바운스(500ms) 유지 전략 확정.
  - `ThreadBodyDisplay`에서 `is_markdown`에 따라 마크다운 렌더링 분기 적용.
  - 완료 기준: 스레드 작성/편집에서 라이브 렌더링 제공.

- Phase 4: 댓글/답글 작성 화면 적용
  - `EntryComposer`, `ReplyComposer`에 Milkdown 적용.
  - 작은 입력 영역에서 에디터 높이/스크롤 UX 점검.
  - 완료 기준: 댓글/답글 작성에서 라이브 렌더링 제공.

- Phase 5: 댓글 편집 적용 및 일관성 점검
  - `EntryEditor` 적용 여부 결정 후 반영.
  - 실제 표시 화면(피드/상세)과 에디터 렌더 결과 일치 여부 점검.
  - 완료 기준: 표시/편집 간 문법 불일치 최소화.

## 리스크 및 대응
- 전환 비용: textarea 기반에서 에디터 기반으로 구조 전환 필요
  - 대응: 공통 래퍼로 도입 범위를 좁히고 단계적으로 적용.
- 렌더링 성능 저하: 긴 텍스트/다중 에디터에서 비용 증가 가능
  - 대응: 500ms 디바운스 유지, 에디터 인스턴스 수 최소화, 메모이제이션.
- 보안 이슈(XSS): 마크다운 내 링크/HTML 처리 위험
  - 대응: HTML 비허용, sanitizer 적용, 링크 스킴 제한.

## 검증 계획
- 단위 수준
  - 마크다운 직렬화/역직렬화 케이스 테스트.
- 수동 검증
  - 스레드/댓글/답글 작성 화면에서 라이브 렌더링 확인.
  - 링크/코드/목록 등 주요 문법 렌더링 확인.
  - 실제 게시 후 표시 결과와 편집 내용 일치 여부 확인.
## 마이그레이션 절차
- schema 변경
  - `threads` 테이블에 `is_markdown` BOOLEAN 컬럼 추가(기본값 false).
  - `entries` 테이블에 `is_markdown` BOOLEAN 컬럼 추가(기본값 false).
- 데이터 백필
  - 기존 레코드는 모두 `is_markdown=false`로 유지.
  - 신규 작성 데이터는 애플리케이션 레이어에서 `is_markdown=true`로 설정.
- 롤아웃 순서
  - 1) DB 마이그레이션 적용
  - 2) 백엔드 배포(필드 읽기/쓰기 반영)
  - 3) 프론트 배포(렌더링/표시 로직 반영)

## 백엔드 재부팅 절차
- 배포 전
  - 마이그레이션 스크립트 준비 및 롤백 계획 확인.
- 배포/재부팅 순서
  - 1) 서비스에 연결된 워커/앱 인스턴스 중 1대 이상 트래픽 유지
  - 2) DB 마이그레이션 실행
  - 3) 백엔드 순차 재기동(롤링 재시작)
  - 4) 헬스체크 및 오류 로그 확인
- 배포 후
  - 신규 작성 데이터가 `is_markdown=true`로 저장되는지 확인
  - 기존 데이터가 `is_markdown=false`로 유지되는지 샘플 검증
