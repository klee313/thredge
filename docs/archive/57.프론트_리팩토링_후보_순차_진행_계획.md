# 프론트 리팩토링 후보 순차 진행 계획

## 배경/문제
- 프론트엔드 전반을 톱다운으로 훑어 리팩토링 후보를 정리했으나, 실제 개선을 순차적으로 진행하기 위한 실행 계획이 없다.
- 후보 간 중복/의존 관계가 있어 순서 없이 진행하면 범위가 커지거나 회귀 위험이 높다.

## 목표
- `docs/refactor_candidates_frontend.md`에 정리된 후보를 **순서대로** 실행한다.
- 각 단계에서 동작 동일성을 보장하고, 변경 범위를 통제한다.

## 범위
- 포함: `frontend/src` 내 후보 14개 파일을 순차적으로 리팩토링.
- 제외: 백엔드/인프라/DB 스키마 변경, 기능 추가.

## 현재 동작 정리
- 엔트리포인트에서 `AppShell` → 라우트 → 각 화면/컨트롤러/훅 구조로 구성.
- 홈 피드/상세 페이지는 대규모 props 전달 구조이며, 카테고리 UI는 중복 로직이 존재.

## 개선 방향
- 책임 분리(훅/컴포넌트 분리)와 중복 제거 중심.
- 서버 부하와 UX가 상충할 때 **서버 부하 최소화 우선**.
- 단계별로 리팩토링 후 동일 동작을 유지.

## 단계별 계획

### Phase 1: 전역 레이아웃/라우트 기반 정리
- 대상: `frontend/src/components/layout/AppShell.tsx`
- 변경: 테마/언어/에러 사이드이펙트 분리 훅 도입
- 완료 기준: 렌더 결과 동일, 전역 테마/언어 동작 동일, 글로벌 에러 배너 동작 동일

### Phase 2: 아카이브/설정/관리자 페이지 분리
- 대상: `frontend/src/routes/ArchivePage.tsx`, `frontend/src/routes/SettingsPage.tsx`, `frontend/src/routes/AdminPage.tsx`
- 변경: 섹션 컴포넌트/훅 분리, 공통 렌더링 패턴 정리
- 완료 기준: 검색/복구/설정 저장/비밀번호 변경/관리자 기능 모두 동일 동작

### Phase 3: 카테고리 UI 공통화
- 대상: `frontend/src/components/home/CategoryFilterBar.tsx`, `frontend/src/components/home/ThreadCategorySelector.tsx`
- 변경: 검색/정렬/표시 로직 공통 훅 또는 뷰모델 분리
- 완료 기준: 카테고리 선택/검색/생성/키보드 네비게이션 동일

### Phase 4: 스레드 카드/엔트리 UI 정리
- 대상: `frontend/src/components/home/ThreadCardView.tsx`, `frontend/src/components/home/EntryCard.tsx`, `frontend/src/components/threadDetail/ThreadDetailEntries.tsx`
- 변경: 뷰모델 도입, 엔트리 섹션 공통화
- 완료 기준: 편집/드래그/리플라이 동작 동일

### Phase 5: 컨트롤러/상태 훅 구조화
- 대상: `frontend/src/hooks/useHomeFeedController.ts`, `frontend/src/hooks/useHomeFeedState.ts`, `frontend/src/hooks/useHomeFeedMutations.ts`, `frontend/src/hooks/useThreadDetailController.ts`
- 변경: 반환 구조 단순화, invalidate 범위 최소화(서버 부하 우선)
- 완료 기준: 데이터 일관성 및 UI 갱신 동작 동일

## 리스크 및 대응
- 리스크: 훅 분리로 인한 의존성 누락, 상태 불일치
  - 대응: 변경 전후 동일 동작 체크리스트 유지
- 리스크: invalidate 범위 축소 시 데이터 갱신 누락
  - 대응: 변경 단위별로 영향 쿼리 확인 후 조건부 invalidate 적용

## 검증 계획
- 수동 검증: 홈 피드/상세/아카이브/설정/관리자 주요 플로우 클릭 테스트
- 캐시 검증: 스레드 생성/수정/엔트리 추가 후 목록 반영 확인
