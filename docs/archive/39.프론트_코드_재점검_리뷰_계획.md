# 프론트 코드 재점검 리뷰 계획

## 배경/문제
- 37번 계획에 따라 단계별 리뷰를 다시 수행해 추가 개선점을 확인할 필요가 있음
- 38번 문서는 참고하지 않고 현재 코드 기준으로 문제 여부를 재검증해야 함

## 목표
- 37번 단계 기준으로 프론트 전반을 재점검한다
- 단계별로 “문제/리스크/개선 포인트”를 재정리한다
- 우선순위를 제안해 다음 개선 사이클의 범위를 명확히 한다

## 범위
- 포함: `frontend` 전반(구조, 상태 관리, 컴포넌트, API 연동, 성능, 테스트, i18n)
- 제외: 백엔드/인프라/배포 파이프라인 변경

## 현재 동작 정리
- Vite + React + TS 구성, Tailwind 기반 UI
- `App`에서 인증/테마 적용 및 상단 네비게이션 제공
- 홈 피드/스레드 상세는 별도 라우트로 분리되어 있으며, 각 화면에서 데이터 로딩/액션을 처리

## 개선 방향
- 유지보수성: 대형 컴포넌트 분리, 책임 단위 명확화
- 안정성: 타입 불일치/런타임 리스크 제거
- 접근성/i18n: 하드코딩 제거 및 접근성 기본 보장
- 데이터 계층: 캐시 키/스키마 정합성 유지

## 단계별 계획
- Step 0: 리뷰 범위/설정 파일 점검
  - 대상 파일/폴더: `frontend/README.md`, `frontend/package.json`, `frontend/vite.config.ts`, `frontend/tsconfig*.json`, `frontend/eslint.config.js`, `frontend/tailwind.config.cjs`, `frontend/postcss.config.cjs`
  - 확인 포인트: 빌드/테스트 스크립트, 린트/타입 규칙, 템플릿 문서 여부
  - 재점검 결과
    - `frontend/README.md`가 Vite 기본 템플릿 그대로여서 실제 프로젝트 구동/환경/규칙 문서화가 부족함
    - ESLint가 타입-aware 규칙을 사용하지 않아 구조적 타입 오류를 사전에 잡기 어려움
  - 조치 내용
    - `frontend/README.md`를 프로젝트 안내 중심으로 교체 (환경 변수/스크립트/규칙 명시)
    - ESLint에 type-aware 설정 추가 (`recommendedTypeChecked` + project 참조)
  - 완료 기준: 문서/규칙 갭 목록 정리

- Step 1: 엔트리포인트/라우팅/전역 스타일 점검
  - 대상 파일/폴더: `frontend/src/main.tsx`, `frontend/src/App.tsx`, `frontend/src/router.tsx`, `frontend/src/routes/*.tsx`, `frontend/src/index.css`
  - 확인 포인트: 라우트 구조, 전역 책임 분리, 404/가드 여부
  - 재점검 결과
    - 라우터에 404/에러 라우트가 없어 잘못된 경로 대응이 비어 있음
    - `admin` 라우트는 존재하나 전역 가드 없이 내부에서만 차단됨(UX/보안 관점 개선 여지)
    - `main.tsx`에서 QueryClient가 생성되지만 전역 에러 핸들링/로딩 UI 기준이 없음(페이지별 중복 처리 가능성)
    - `index.css`의 기본 테마 변수는 하드코딩되어 있고 테마 변경은 JS로만 적용됨(초기 로드 플래시 가능성)
  - 조치 내용
    - 404 전용 페이지 추가 및 라우터에 `*` 경로 등록
    - Admin 라우트 전용 가드 컴포넌트 추가로 라우팅 레벨 차단 적용
    - QueryClient 전역 에러 로깅 핸들러 추가
    - 테마 적용 `useLayoutEffect`로 변경해 초기 플래시 완화
  - 완료 기준: 라우팅 리스크 목록 정리

- Step 2: 핵심 화면/컴포넌트 구조 점검
  - 대상 파일/폴더: `frontend/src/components/home/**`, `frontend/src/components/CategoryInlineCreator.tsx`, `frontend/src/components/common/**`, `frontend/src/routes/ThreadDetailPage.tsx`
  - 확인 포인트: 컴포넌트 책임/props 경계, 재사용성, 복잡도
  - 재점검 결과
    - `HomeFeed`가 데이터 로딩/필터/상태/액션을 모두 포함해 책임이 과밀함
    - `ThreadCard`에서 `EntryDetail` 타입을 import하지 않아 타입 오류 가능성 존재
    - `SearchForm` 입력에 명시적 label/aria-label이 없어 접근성 기본 요건 미흡
    - `ThreadCard`가 `EntryList`/드래그/조회까지 포함해 단일 컴포넌트 복잡도가 높음
    - `ThreadDetailPage`와 `ThreadCard` 사이에서 일부 렌더/UI 로직이 중복되어 유지보수 비용 증가 가능
  - 조치 내용
    - `HomeFeedComposer` 분리로 상단 작성/검색 UI 책임 분리
    - `ThreadBodyDisplay` 공통 컴포넌트 추가로 상세/카드 렌더 중복 완화
    - `ThreadCard`의 `EntryDetail` 타입 import 보강
    - `SearchForm`에 label/aria-label 추가
  - 완료 기준: 구조/접근성 개선 후보 정리

- Step 3: 훅/상태 전파 경로 점검
  - 대상 파일/폴더: `frontend/src/hooks/*.ts`, `frontend/src/store/settingsStore.ts`
  - 확인 포인트: 상태 소유권, URL/localStorage 동기화 규칙, 훅 간 결합
  - 재점검 결과
    - `useHomeFeedState`의 `tab` 쿼리 값 검증이 없어 예상 밖 값 유입 시 UI가 비정상 탭으로 고정될 수 있음
    - `useHomeFeedState`에서 검색어를 비우더라도 `tab=search`가 유지되어 사용자가 기대하는 기본 탭 복귀가 안 될 수 있음
    - `usePinchFontSize`가 전역 touchmove를 가로채 기본 브라우저 줌을 막음(접근성/사용성 리스크)
  - 조치 내용
    - `tab` 쿼리값 검증 추가 및 검색어 비움 시 기본 탭 복귀
    - 설정 페이지에 핀치 줌 on/off 추가 및 상태 저장
    - 핀치 줌 비활성화 시 앱 줌 제거 및 브라우저 줌 복원
  - 완료 기준: 상태 동기화 리스크 정리

- Step 4: 데이터 계층 및 API 유틸 점검
  - 대상 파일/폴더: `frontend/src/lib/api.ts`, `frontend/src/lib/queryKeys.ts`, `frontend/src/lib/threadCache.ts`
  - 확인 포인트: 캐시 키 안정성, 타입 정합성, 에러 처리 일관성
  - 재점검 결과
    - `queryKeys.threads.search/feedFiltered`에서 `categoryIds` 배열 정렬이 고정되지 않아 캐시 키 중복 가능
    - `threadCache`에서 `ThreadFeedItem`에 존재하지 않는 `entries`를 가정해 업데이트하는 부분이 있어 타입/실데이터 불일치 위험
    - `threadCache.updateEntryInFeed`가 `ThreadFeedItem`에 없는 `entries` 배열을 갱신하려 하므로 실제로는 무효 업데이트가 될 가능성 있음
    - `api.ts`의 `requestJson`/`requestEmpty` 에러 메시지 포맷이 화면별로 그대로 노출될 수 있어 UX 일관성 저해 가능
  - 조치 내용
    - `queryKeys`에서 `categoryIds` 정렬 고정으로 캐시 키 안정화
    - feed 항목에 `entries`가 있는 경우에만 갱신하도록 보호 로직 추가
    - API 에러를 `ApiError`로 통일해 UI 메시지 일관성 확보
  - 완료 기준: 데이터 계층 정합성 이슈 정리

- Step 5: UI 토큰/유틸/국제화 점검
  - 대상 파일/폴더: `frontend/src/lib/uiTheme.ts`, `frontend/src/lib/uiTokens.ts`, `frontend/src/lib/mutedText.ts`, `frontend/src/lib/highlightMatches.tsx`, `frontend/src/i18n.ts`, `frontend/src/locales/**`
  - 확인 포인트: 테마 일관성, 안전한 텍스트 처리, i18n 누락
  - 재점검 결과
    - `highlightMatches`가 HTML 태그가 포함된 텍스트에 대해 `dangerouslySetInnerHTML`을 사용함(입력 신뢰 전제 불명확 시 XSS 위험)
    - `완료` 문자열이 하드코딩되어 i18n 키 누락 (`ThreadCard`, `ThreadDetailPage`, `EntryCard`)
    - 링크 자동 변환 시 `target="_blank"`는 사용하지만 링크 텍스트/접근성 라벨은 제공되지 않음
    - `supportedLanguages`와 `i18n` 설정이 동일하지만 UI에서 언어 선택 규칙/표시는 문서화되지 않음
  - 조치 내용
    - `highlightMatches`에 강력 경고 주석 추가 (기존 콘텐츠 호환성 이유로 유지)
    - `common.complete` 키 추가 및 하드코딩 문자열 제거
    - 링크 자동 변환 시 aria-label 추가
    - 프론트 README에 언어 지원 범위/규칙 명시
  - 완료 기준: i18n/보안 리스크 정리

- Step 6: 결과 정리 및 우선순위 제안
  - 변경 내용: 심각도/난이도/효익 기준으로 이슈 분류
  - 우선순위 업데이트
    - P0 (잔존 리스크)
      - `highlightMatches`의 HTML 처리로 인한 XSS 리스크는 현 단계에서 유지(강력 경고 주석으로 관리)
    - P1 (완료)
      - `ThreadCard` 타입 import 누락 해결
      - feed 항목 구조 가정 불일치 보호 로직 추가
      - `queryKeys`의 `categoryIds` 정렬 고정
    - P2 (완료)
      - 404 라우트 추가
      - admin 라우팅 레벨 가드 추가
      - SearchForm 접근성 개선
      - i18n 하드코딩 제거
  - 완료 기준: 우선순위 목록 확정 및 후속 작업 범위 제안

## 리스크 및 대응
