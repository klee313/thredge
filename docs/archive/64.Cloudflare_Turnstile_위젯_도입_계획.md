# Cloudflare Turnstile 위젯 도입 계획

## 배경/문제
- 현재 `로그인/회원가입` 요청은 사용자 입력만으로 처리되어 자동화 봇 트래픽을 애플리케이션 레벨에서 직접 구분하지 못한다.
- 이미 Rate Limit 가이드는 존재하지만(`docs/CLOUDFLARE_RATE_LIMIT_GUIDE.md`), 클라이언트 상호작용 기반 검증(Challenge 통과 여부)을 서버에서 확인하는 경로는 없다.
- 결과적으로 신규 계정 대량 생성, 인증 엔드포인트 과도 호출 같은 위험을 완화할 방어 계층이 부족하다.

## 목표
- 로그인/회원가입 폼에 Cloudflare Turnstile 위젯을 추가하고, 제출 시 발급된 토큰을 서버에서 검증한다.
- 검증 실패 요청은 인증 처리 이전에 차단하여 봇/비정상 트래픽의 인증 진입을 줄인다.
- 운영 환경에서 키/정책을 환경변수 기반으로 관리하고, 로컬 개발에서는 우회 가능한 모드를 제공한다.

## 범위
- 포함 범위
- 프론트엔드 인증 UI(`AuthPanel`)에 Turnstile 렌더링 및 토큰 수집 로직 추가
- `/api/auth/login`, `/api/auth/signup` 요청 바디에 Turnstile 토큰 전달 필드 추가
- 백엔드에서 Cloudflare Siteverify API 호출 기반 토큰 검증 서비스 추가
- 인증 API 진입 시 토큰 검증 실패 처리(400/401 계열 명시적 에러 메시지)
- 운영/개발 설정 문서화(환경변수, 활성화 조건, 실패 시 동작)
- 제외 범위
- Google OAuth 로그인 플로우(`/oauth2/*`)에 Turnstile 강제 적용
- Cloudflare 대시보드 룰/방화벽 정책 자체 생성 작업(문서 가이드만 포함)
- 관리자 페이지, 비인증 일반 API에 대한 추가 CAPTCHA 확장

## 현재 동작 정리
- 프론트 인증 폼은 `frontend/src/components/auth/AuthPanel.tsx`에서 `login/signup` 모드를 전환하며 사용자명/비밀번호만 전송한다.
- 프론트 API 호출은 `frontend/src/lib/api.ts`의 `login(username, password)`, `signup(username, password)`를 사용한다.
- 백엔드 인증 엔드포인트는 `backend/src/main/kotlin/com/thredge/backend/api/AuthController.kt`의 `/api/auth/login`, `/api/auth/signup`이며 Turnstile 검증 단계가 없다.
- 인증 요청 DTO는 `backend/src/main/kotlin/com/thredge/backend/api/dto/AuthDtos.kt`에 정의되어 있고 현재 `username`, `password`만 받는다.
- 환경 설정은 `backend/src/main/resources/application.yml`, `docker-compose.yml`, `frontend/src/lib/env.ts`를 통해 관리되며 Turnstile 관련 키/플래그는 아직 없다.

## 개선 방향
- 인증 정책은 "인증 처리 이전 검증" 원칙으로 설계한다. (Turnstile 실패 시 계정 조회/비밀번호 검증 전에 종료)
- 기능 플래그 기반으로 단계적 롤아웃한다. (`enabled=false`인 환경에서는 기존 동작 유지)
- UI 장애 최소화를 위해 위젯 로드 실패/토큰 만료/재시도 상태를 명시적으로 처리한다.
- API 스키마(OpenAPI)와 프론트 타입 생성 파일을 함께 갱신해 계약 불일치를 방지한다.
- 에러 메시지는 사용자용/운영용(로그) 관점을 분리한다.

## 단계별 계획
- Phase 1. 요구사항/설정 설계
- 변경 내용: Turnstile 적용 대상 엔드포인트, 실패 응답 규약, 환경변수 이름(`APP_AUTH_TURNSTILE_ENABLED`, `APP_AUTH_TURNSTILE_SECRET_KEY`, `VITE_TURNSTILE_SITE_KEY`) 확정
- 완료 기준: 문서에 설정값, 기본값, 환경별 동작(로컬/운영) 명시

- Phase 2. 백엔드 검증 계층 추가
- 변경 내용: Turnstile 검증 서비스(Cloudflare Siteverify 호출)와 요청 DTO 토큰 필드 추가, `AuthController`에서 login/signup 전 검증 훅 적용
- 완료 기준: 토큰 미제공/검증실패/Cloudflare 오류 케이스가 의도한 예외 코드로 반환되고, 활성화 OFF 시 기존 인증 동작 유지

- Phase 3. 프론트 위젯 및 API 연동
- 변경 내용: `AuthPanel`에 Turnstile 위젯 렌더링, 토큰 상태 관리(발급/만료/리셋), `login/signup` API 파라미터에 토큰 포함
- 완료 기준: 로그인/가입 버튼 제출 시 토큰이 함께 전송되며, 토큰 없을 때 사용자 피드백 제공

- Phase 4. 계약/문서/환경 반영
- 변경 내용: OpenAPI 스펙 갱신 후 프론트 generated 타입 재생성, 개발 문서에 Turnstile 설정/테스트 방법 추가
- 완료 기준: `contracts/openapi/openapi.json`과 `frontend/src/lib/api/generated.ts` 동기화, 로컬 실행 가이드 업데이트

- Phase 5. 통합 검증
- 변경 내용: 백엔드 테스트(검증 서비스 단위/컨트롤러), 프론트 기본 렌더링/상태 테스트, 수동 E2E 점검
- 완료 기준: 핵심 시나리오(성공/실패/만료/비활성)가 재현 가능하고 회귀 없음 확인

## 리스크 및 대응
- 리스크: Cloudflare API 지연/장애 시 인증 자체가 막힐 수 있음
- 대응: 타임아웃/예외 처리 정책 정의(기본 fail-closed, 필요 시 환경별 fail-open 옵션 검토), 장애 로그/메트릭 추가

- 리스크: 프런트 위젯 스크립트 로드 실패로 로그인 UX 저하
- 대응: 로드 실패 메시지와 재시도 동선 제공, 버튼 비활성 조건 명확화

- 리스크: 비밀키 노출 또는 환경변수 누락
- 대응: 서버 전용 secret 키와 클라이언트 site key 분리, 설정 누락 시 애플리케이션 시작 경고/명시적 오류

- 리스크: OpenAPI/프론트 타입 미동기화로 빌드 오류
- 대응: 타입 생성 스크립트(`npm run openapi:types`)를 변경 절차에 고정

## 검증 계획
- 백엔드 자동 검증
- Turnstile 검증 서비스 단위 테스트: 성공/실패/네트워크 오류/타임아웃
- 인증 컨트롤러 테스트: 토큰 없음, 잘못된 토큰, 정상 토큰, 기능 비활성 케이스

- 프론트 자동 검증
- 인증 패널 테스트: 모드 전환, 토큰 없음 시 제출 차단, 토큰 수신 후 제출 성공 경로
- API 함수 테스트 또는 타입 검증: 새 요청 필드 포함 여부 확인

- 수동 검증 절차
- [ ] Turnstile 활성화 + 정상 토큰으로 로그인/가입 성공
- [ ] 토큰 만료 후 재검증 요구 동작 확인
- [ ] 잘못된 토큰 제출 시 사용자 오류 메시지 확인
- [ ] Turnstile 비활성 환경에서 기존 로그인/가입 정상 동작 확인
