# 65. Archive 하드삭제 기능 계획

## 배경/문제
- 현재 Archive에서는 숨김(soft delete) 상태의 스레드/댓글을 복원할 수만 있고, 완전 삭제(hard delete)할 수 없다.
- 사용자가 정리 목적에서 "정말로 지우기"를 원할 때 수동 우회(DB 직접 작업) 없이 앱 내에서 처리할 수 있어야 한다.
- 현재 스키마는 `is_hidden` 기반 soft delete만 존재하며, `deleted_at`/`hidden_at` 시간 컬럼이 없어 기간 기반 정리 정책은 이번 작업 대상이 아니다.

## 목표
- Archive 화면에서 스레드/댓글에 대해 "영구 삭제" 액션을 제공한다.
- 영구 삭제 전 경고/확인 절차를 통해 오삭제 위험을 낮춘다.
- 삭제 수행 시 실제 DB 레코드를 제거하고, 화면/캐시를 일관되게 갱신한다.

## 범위
- 포함 범위
  - Archive UI에 영구 삭제 버튼 및 경고 확인 플로우 추가
  - 스레드/댓글 하드삭제 API 추가
  - 서비스 계층에서 소유권 검증 + soft delete 상태 검증 후 실제 삭제 로직 구현
  - 프론트 캐시 무효화 및 성공/실패 피드백 반영
- 제외 범위
  - 기간 기반 자동 삭제(배치, 스케줄러)
  - `deleted_at`/`hidden_at` 컬럼 추가
  - 관리자용 일괄 purge 기능

## 현재 동작 정리
- `DELETE /api/threads/{id}`는 soft delete(`isHidden=true`)로 동작한다.
- `POST /api/threads/{id}/restore`, `POST /api/entries/{id}/restore`로 복원 가능하다.
- Archive는 `isHidden=true` 데이터를 조회/검색해서 표시한다.
- DB FK는 cascade 설정이 없어, hard delete 시 연관 데이터 삭제 순서를 서비스에서 보장해야 한다.

## 개선 방향
- 기존 soft delete API는 유지하고, hard delete는 별도 명시적 API로 분리한다.
- "Archive에서만 가능한 위험 작업"이라는 UX를 유지한다.
- 하드삭제 대상은 `isHidden=true` 상태인 리소스로 제한한다.
- 트랜잭션으로 삭제를 감싸 중간 실패 시 일관성을 보장한다.

## 단계별 계획
- Phase 1: API 계약 정의
  - 변경
    - 스레드/댓글 하드삭제 엔드포인트 추가
    - 라우트 명은 soft delete와 혼동되지 않게 `purge` 계열로 분리
  - 완료 기준
    - 컨트롤러 경로/HTTP 메서드 확정 및 OpenAPI 반영 포인트 정리

- Phase 2: 백엔드 삭제 로직 구현
  - 변경
    - 소유권 검증
    - `isHidden=true` 선검증(아니면 409 또는 400)
    - 스레드 삭제 시 연관 데이터 순차 삭제(`thread_categories` -> `entries` -> `thread`)
    - 댓글 삭제 정책
      - 현재 적용안: 자식 댓글이 있으면 영구삭제 거부(leaf-only)
  - 완료 기준
    - 트랜잭션 내에서 FK 오류 없이 삭제 완료
    - 실패 케이스(권한 없음/숨김 아님/미존재) 응답 일관성 확보

- Phase 3: 프론트 Archive UI 연결
  - 변경
    - 숨김 스레드/숨김 댓글 카드에 "영구 삭제" 버튼 추가
    - 2단계 경고(확인 모달/confirm) 적용
    - 성공 시 목록에서 즉시 제거, 관련 query invalidate
  - 완료 기준
    - 사용자 플로우에서 경고 후 삭제가 정상 동작
    - 기존 복원 버튼 동작과 충돌 없음

- Phase 4: 문구/에러/관찰성 정리
  - 변경
    - i18n 키 추가(영구 삭제, 경고문, 완료/실패 메시지)
    - 오류 메시지 표준화
  - 완료 기준
    - ko/en/tr 기준 최소 문구 누락 없음

## 리스크 및 대응
- FK 제약으로 인한 삭제 실패
  - 대응: 삭제 순서를 서비스에서 고정하고 트랜잭션 적용
- 사용자 오삭제
  - 대응: 경고 문구 + 재확인 절차 + Archive 한정 노출
- soft/hard 삭제 API 혼동
  - 대응: 엔드포인트/버튼 라벨을 명확히 분리(`숨기기` vs `영구 삭제`)
- 캐시 불일치
  - 대응: Archive/Feed/Detail 관련 query invalidate 범위 명시

## 검증 계획
- 백엔드
  - 숨김 상태 스레드/댓글 hard delete 성공
  - 숨김이 아닌 대상 hard delete 실패
  - 타 사용자 리소스 hard delete 실패
- 프론트
  - Archive에서 경고 후 삭제 요청 전송 확인
  - 성공 시 목록 제거 및 토스트/피드백 표시
  - 실패 시 에러 표시 및 UI 복구
- 수동 검증 절차
  - 1) 스레드/댓글을 숨김 처리
  - 2) Archive에서 영구 삭제 클릭
  - 3) 경고 확인 후 삭제
  - 4) Archive/검색/상세에서 대상이 완전히 사라졌는지 확인
