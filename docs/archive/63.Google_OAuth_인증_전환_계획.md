# Google OAuth 인증 전환 계획

## 배경/문제
- 현재 인증은 자체 아이디/비밀번호 + 서버 세션 기반(`THREDGE_SESSION`)이다.
- 인증 UI가 로그인/회원가입 폼 중심이라 Google OAuth 기반 로그인 경험과 맞지 않는다.
- 인증 진입점과 세션 유지 정책은 있으나, OAuth 콜백/상태값(state)/리다이렉트 경로가 없다.
- 향후 외부 인증으로 전환할 때 백엔드 보안 설정, 프론트 라우팅, 로그인 화면 UX를 함께 정리할 필요가 있다.

## 목표
- Google OAuth를 1차 로그인 수단으로 도입한다.
- 로그인 화면에 Google OAuth 버튼을 추가하고, 버튼 클릭으로 OAuth 플로우를 시작한다.
- 백엔드는 OAuth 콜백을 처리해 기존 세션 인증 모델과 연결한다.
- 기존 API 인증 방식(세션 기반)을 유지하면서 로그인 진입점만 OAuth 중심으로 전환한다.

## 범위
- 포함 범위
  - 백엔드 OAuth 클라이언트 설정 및 인증 흐름 추가
  - 로그인/콜백 프론트 라우트 및 Google 로그인 버튼 UI 추가
  - 사용자 매핑 정책(최초 로그인 시 계정 생성 또는 기존 계정 연결) 정의
  - 인증 관련 환경변수/설정 문서 업데이트
  - 전환 후 Rate Limit 정책 기준 재정의
- 제외 범위
  - Apple/GitHub 등 추가 OAuth 공급자
  - 모바일 네이티브 앱용 OAuth 플로우
  - MFA/Passkey 도입
  - 완전한 JWT 무상태 인증 전환

## 현재 동작 정리
- 보안 정책: `/api/auth/login`, `/api/auth/signup`, `/api/auth/logout`은 공개, 나머지는 인증 필요  
  - `backend/src/main/kotlin/com/thredge/backend/config/SecurityConfig.kt`
- 로그인 처리: `UsernamePasswordAuthenticationToken`으로 인증 후 세션 저장  
  - `backend/src/main/kotlin/com/thredge/backend/api/AuthController.kt`
- 세션 저장소: JDBC 세션(`spring-session-jdbc`), 쿠키명 `THREDGE_SESSION`, 7일 만료  
  - `backend/src/main/resources/application.yml`
  - `backend/build.gradle.kts`
- 프론트 인증 요청: `fetch(..., { credentials: 'include' })`로 쿠키 사용  
  - `frontend/src/lib/api.ts`
- 로그인 UI: `AuthPanel`이 로그인/회원가입 폼 렌더링  
  - `frontend/src/components/auth/AuthPanel.tsx`
  - `frontend/src/routes/LoginPage.tsx`

## 개선 방향
- 인증 저장 방식은 당장 세션 유지(위험 최소화), 로그인 진입만 Google OAuth로 교체한다.
- OAuth 시작/콜백 책임은 백엔드에 두고, 프론트는 버튼/상태 표시/오류 안내에 집중한다.
- 계정 식별 키는 Google `sub`를 기준으로 별도 컬럼에 보관해 이메일 변경 리스크를 줄인다.
- 롤아웃은 점진적으로 진행한다(기존 로컬 계정 로그인과 병행 가능 기간 운영).

## 단계별 계획

### Phase 1. 백엔드 OAuth 기반 마련
- 변경 내용
  - `spring-boot-starter-oauth2-client` 의존성 추가  
    - `backend/build.gradle.kts`
  - OAuth client registration/provider 설정 추가  
    - `backend/src/main/resources/application.yml`
  - Spring Security 설정에 OAuth 로그인 플로우 추가  
    - `backend/src/main/kotlin/com/thredge/backend/config/SecurityConfig.kt`
  - 성공/실패 핸들러에서 기존 세션 인증과 연계
    - 신규 파일 후보: `backend/src/main/kotlin/com/thredge/backend/security/OAuth2LoginSuccessHandler.kt`
    - 신규 파일 후보: `backend/src/main/kotlin/com/thredge/backend/security/OAuth2LoginFailureHandler.kt`
- 완료 기준
  - `/oauth2/authorization/google` 진입 시 Google 로그인 화면으로 리다이렉트된다.
  - OAuth 성공 후 백엔드가 세션을 생성하고 `/api/auth/me`가 200 응답한다.

### Phase 2. 사용자 도메인/매핑 정책 반영
- 변경 내용
  - `UserEntity`에 OAuth 식별 필드 추가(예: `provider`, `providerSubject`, `email`)  
    - `backend/src/main/kotlin/com/thredge/backend/domain/entity/UserEntity.kt`
  - 저장소 조회 메서드 추가(예: `findByProviderAndProviderSubject`)  
    - `backend/src/main/kotlin/com/thredge/backend/domain/repository/UserRepository.kt`
  - 마이그레이션 추가(Flyway)  
    - `backend/src/main/resources/db/migration/Vxx__add_oauth_identity_columns.*.sql`
  - 최초 로그인 사용자 생성/기존 사용자 연결 서비스 추가  
    - 신규 파일 후보: `backend/src/main/kotlin/com/thredge/backend/service/OAuthUserProvisioningService.kt`
- 완료 기준
  - 동일 Google 계정 재로그인 시 같은 내부 사용자에 매핑된다.
  - 중복 사용자 생성이 발생하지 않는다.

### Phase 3. 인증 API/호환 경로 정리
- 변경 내용
  - `AuthController`에서 로컬 로그인/회원가입 유지 여부를 feature flag로 분리
    - `backend/src/main/kotlin/com/thredge/backend/api/AuthController.kt`
  - OAuth 시작/콜백/상태 확인용 경로 정의
    - 필요 시 신규 컨트롤러: `backend/src/main/kotlin/com/thredge/backend/api/OAuthController.kt`
  - 에러 응답 포맷 정리(콜백 실패 시 프론트가 처리 가능한 코드/메시지)
- 완료 기준
  - 운영 플래그로 `local-login on/off` 전환이 가능하다.
  - OAuth 실패 시 사용자에게 일관된 오류 메시지가 전달된다.

### Phase 4. 프론트 로그인 화면 개편 (Google 버튼 포함)
- 변경 내용
  - `AuthPanel`에 "Google로 로그인" 버튼 추가
    - `frontend/src/components/auth/AuthPanel.tsx`
  - 버튼 클릭 시 OAuth 시작 URL로 이동(백엔드 경유)
    - `window.location.href = '/oauth2/authorization/google'` 또는 API base 결합 유틸 사용
  - OAuth 콜백 후 결과 처리 라우트 추가(예: `/login/callback`)
    - `frontend/src/routes/appRoutes.tsx`
    - 신규 파일 후보: `frontend/src/routes/OAuthCallbackPage.tsx`
  - 기존 아이디/비번 폼은 전환 기간 동안 옵션으로 유지하거나 숨김 처리
  - i18n 문구 추가(ko/en/tr)
    - `frontend/src/locales/ko.json`
    - `frontend/src/locales/en.json`
    - `frontend/src/locales/tr.json`
- 완료 기준
  - 로그인 페이지에서 Google 버튼이 렌더링되고 동작한다.
  - 콜백 후 홈으로 정상 이동하며 인증 상태가 갱신된다.

### Phase 5. 인프라/보안/운영 반영
- 변경 내용
  - 환경변수 추가
    - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`
    - 프론트 기준 리다이렉트 URL 정합성 점검
  - CORS/Origin 및 쿠키 보안 설정 강화(`Secure`, `SameSite`, `HttpOnly` 확인)
    - `backend/src/main/resources/application.yml`
    - `backend/src/main/kotlin/com/thredge/backend/config/WebConfig.kt`
  - Cloudflare Rate Limit 룰 업데이트(OAuth 엔드포인트 포함)
    - 참조: `docs/CLOUDFLARE_RATE_LIMIT_GUIDE.md`
- 완료 기준
  - 운영 도메인에서 OAuth redirect mismatch가 발생하지 않는다.
  - OAuth 시작/콜백/토큰 교환 구간이 룰에 포함된다.

### Phase 6. 테스트/전환/정리
- 변경 내용
  - 인증 관련 통합 테스트 추가
    - `backend/src/test/kotlin/...` (OAuth 성공/실패, 사용자 매핑)
  - 프론트 로그인 플로우 테스트 갱신
    - `frontend/src/components/...*.test.tsx`
  - 전환 기간 후 로컬 로그인 제거 여부 결정 및 코드 정리
- 완료 기준
  - 핵심 인증 시나리오 자동 테스트 통과
  - 전환 후 로그인 관련 회귀 이슈가 재현되지 않는다.

## 리스크 및 대응
- OAuth redirect URI 오설정으로 로그인 실패
  - 대응: 환경별 redirect URI 표준화, 배포 전 체크리스트 운영
- 사용자 매핑 충돌(기존 로컬 계정과 Google 계정 연결 문제)
  - 대응: `provider + providerSubject`를 1순위 식별자로 사용, 병합 정책 문서화
- 쿠키 전송 이슈(SameSite/Secure 미스매치)
  - 대응: 로컬/운영 환경별 쿠키 정책 분리, 브라우저별 수동 검증
- 운영 초기에 Rate Limit 과차단
  - 대응: 1주간 Challenge 중심으로 관찰 후 Block 강화

## 검증 계획
- 백엔드 수동 검증
  - `/oauth2/authorization/google` 진입 후 인증 성공/실패 흐름 점검
  - `/api/auth/me`가 세션 기준으로 정상 응답하는지 확인
- 프론트 수동 검증
  - 로그인 페이지 Google 버튼 노출/클릭/리다이렉트 동작 확인
  - 콜백 후 홈 이동 및 헤더 로그인 상태 반영 확인
- 운영 전 체크
  - Google Cloud Console의 Authorized redirect URI와 실제 배포 URL 일치 확인
  - Cloudflare Rate Limit 룰이 OAuth 관련 경로에 적용되는지 확인
