# is_markdown 편집 상태 분리 리팩토링 계획

## 배경/문제
- is_markdown 토글 추가로 인해 편집 상태가 여러 레이어(상태 훅 → 어댑터 → 뷰 → 섹션 → 에디터)를 타고 내려가면서 변경 지점이 급증했다.
- 작은 필드 변경이 캐시/렌더링/편집 상태 전반에 영향을 주는 구조로, 결합도와 변경 비용이 높다.
- 결과적으로 기능 추가 시 수정 범위가 커지고, 실수로 인한 회귀 위험이 커진다.

## 목표
- is_markdown 같은 “편집 전용 필드”의 전달 경로를 단축한다.
- 편집 상태와 표시 상태를 분리해, 변경 영향 범위를 줄인다.
- 업데이트 후 화면 반영은 유지하되, 캐시 패치 로직을 최소화한다.

## 범위
- 포함 범위
  - 스레드/댓글 편집 상태 흐름 단순화
  - is_markdown 토글의 전달 경로 축소
  - 캐시 업데이트 로직 단순화(필요 최소화)
- 제외 범위
  - 도메인 모델/DB 스키마 변경
  - API 스펙 변경
  - 마크다운 렌더링 구현 자체 변경

## 현재 동작 정리
- 편집 상태는 `useThreadUiState` → `useHomeFeedState`/`useThreadDetailState` → 어댑터/뷰/섹션을 통해 props로 전달된다.
- entry/thread 업데이트 후 캐시 패치를 여러 위치에서 수행한다.
- is_markdown은 thread/entry 편집 UI와 렌더링 모두에 관여하여 전달 경로가 길어진다.

## 개선 방향
- 편집 상태는 **에디터 컴포넌트 로컬** 또는 **전용 컨트롤러 훅**으로 이동한다.
- 화면 표시 상태(렌더링용)와 편집 상태(에디터용)를 명확히 분리한다.
- 업데이트 성공 시 **invalidate 중심**으로 전환하고, 캐시 패치는 필요한 최소 범위만 유지한다.

## 단계별 계획
- Phase 1: 구조 분해 준비
  - 스레드/댓글 편집 관련 props/상태 흐름을 문서화한다.
  - is_markdown 전달 경로를 식별하고 실제 의존 지점을 확정한다.
  - 완료 기준: 편집 상태 전달 경로와 의존 컴포넌트 목록이 정리됨.

- Phase 2: 편집 상태 로컬화
  - ThreadEditor/EntryEditor에서 편집 상태(is_markdown 포함)를 로컬로 보관하도록 변경한다.
  - 상위 컴포넌트에는 “초기값”과 “저장 시 콜백”만 전달하도록 축소한다.
  - 완료 기준: 상위 상태 훅과 어댑터에서 is_markdown 전달이 제거됨.

- Phase 3: 캐시 패치 최소화
  - 업데이트 성공 시 invalidate 중심으로 전환하고, 필수 패치만 유지한다.
  - thread/entry 업데이트 로직의 중복 경로를 정리한다.
  - 완료 기준: 캐시 업데이트 경로 수가 감소하고 동작 일관성 유지됨.

- Phase 4: 정리 및 회귀 점검
  - 편집/저장/렌더링 플로우 확인
  - 문서 및 주석 업데이트
  - 완료 기준: 기존 기능 회귀 없이 리팩토링 완료

## 리스크 및 대응
- 리스크: 로컬 상태 전환 시 저장/취소 동작이 달라질 수 있음
  - 대응: 기존 UI 플로우와 동일한 시나리오로 수동 테스트 수행
- 리스크: invalidate 중심 전환 시 UX 지연 가능
  - 대응: 필요한 최소 패치는 유지하고, 과도한 invalidate는 제한

## 검증 계획
- 수동 검증
  - 스레드 편집에서 마크다운 토글 → 저장 → 카드/상세 렌더링 확인
  - 댓글 편집에서 마크다운 토글 → 저장 → 카드/상세 렌더링 확인
  - 편집 취소 시 상태 초기화 정상 동작 확인
- 최소 테스트
  - threadCache 관련 단위 테스트가 필요한 경우 범위를 재정의
