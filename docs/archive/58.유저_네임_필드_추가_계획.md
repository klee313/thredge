# 유저 네임 필드 추가 계획

## 배경/문제
- 현재 사용자 식별은 아이디(영문/숫자/언더바)만으로 이뤄져 있고, 표시 이름을 유연하게 설정할 수 없다.
- 아이디는 제한된 문자셋이 필요하지만, 표시용 이름은 국제화/개성 표현을 위해 유니코드 전반을 허용해야 한다.

## 목표
- 사용자마다 `name`(표시 이름) 필드를 추가한다.
- 아이디는 기존 제약(영문/숫자/언더바)을 유지하고, `name`은 유니코드를 허용한다.
- 백엔드부터 프론트까지 일관되게 반영된다.

## 범위
- 포함
  - DB 스키마에 `users.name`(또는 동등) 필드 추가 및 마이그레이션
  - API/도메인 모델에 `name` 필드 추가
  - 입력/수정 API에 `name` 검증 규칙 반영
  - 프론트 설정/프로필/표시 영역에 `name` 노출
- 제외
  - 검색/정렬/필터 기준 변경
  - 다국어 이름 정규화/동등 비교 고도화(필요 시 후속 작업)

## 현재 동작 정리
- 사용자 식별은 아이디 기반(영문/숫자/언더바)으로 운영되고 있음.
- 프론트에서는 사용자 표시에 `username`만 사용하고 있음.

## 개선 방향
- `id`(또는 username)는 고정된 식별자, `name`은 자유 입력 표시용 필드로 분리한다.
- `name`은 유니코드 허용, 최소/최대 길이와 공백 처리 규칙을 둔다.
- 마이그레이션 시 기존 사용자는 기본값을 안전하게 채운다(예: `name = username`).

## 단계별 계획
- 1단계: 스키마/마이그레이션
  - users 테이블에 `name` 컬럼 추가(널 허용 여부 결정).
  - 기존 레코드에 기본값 채우기(예: `username` 복사).
  - 완료 기준: 마이그레이션 적용 후 읽기 API에서 `name` 반환 가능.
- 2단계: 백엔드 모델/검증/API
  - 사용자 DTO/모델에 `name` 추가.
  - 생성/수정 API에 `name` 검증 반영(유니코드 허용, 길이 제한, 트림 규칙).
  - 완료 기준: 유효/무효 케이스가 명확하고 API가 일관된 에러를 반환.
- 3단계: 프론트 입력/표시 연동
  - 프로필/설정 UI에 `name` 입력 추가.
  - 표시 영역에서 `name`을 우선 사용하고, 없을 경우 `username` 폴백.
  - 완료 기준: 저장/새로고침 후 `name`이 반영됨.
- 4단계: 통합 점검
  - 대표 시나리오(가입/수정/표시) 확인.
  - 완료 기준: 주요 화면에서 아이디와 네임의 역할이 혼동되지 않음.

## 리스크 및 대응
- 표시 이름과 아이디 혼동 가능성
  - 대응: UI 레이블 분리(아이디/네임 명확히 구분).
- 유니코드 입력으로 인한 폭 넓은 렌더링/정렬 이슈
  - 대응: 길이 제한 및 기본 폴백 유지.
- 기존 사용자 데이터 마이그레이션 누락
  - 대응: 마이그레이션 스크립트에 기본값 채우기 포함.

## 검증 계획
- 백엔드
  - 생성/수정 API에서 `name` 유효성(유니코드 허용, 길이 제한, 공백만 입력 차단) 테스트.
- 프론트
  - 이름 저장 후 재진입 시 표시값 유지.
  - 이름 미설정 시 `username` 폴백 정상 동작 확인.
- 수동 확인
  - 유니코드(예: 한글/이모지/혼합) 입력/표시 확인.
