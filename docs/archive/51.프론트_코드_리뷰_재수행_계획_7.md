# 프론트 코드 리뷰 재수행 계획 7

## 배경/문제
- 37번 계획과 동일한 기준으로 리뷰를 다시 수행해 누락된 검토 항목이 없는지 확인할 필요가 있음
- 38-50번 문서의 결론을 참조하지 않고, 동일한 절차로 독립적인 재점검을 진행하려는 목적

## 목표
- 37번 계획의 단계별 절차를 그대로 적용해 프론트 코드의 이슈/개선 포인트를 재식별한다
- 기존 결과와 무관하게 새로운 관찰 결과를 산출한다
- 추가로 검토할 영역이 있는지 판단 근거를 확보한다

## 범위
- 포함: `frontend` 디렉토리 전반(구조, 상태 관리, 컴포넌트, API 연동, 성능, 테스트)
- 제외: 백엔드/인프라/데이터 파이프라인 상세 코드 리뷰

## 현재 동작 정리
- 37번 계획의 대상 파일/폴더 순서를 그대로 따라가며 코드 흐름을 재정리한다
- 엔트리포인트 → 라우팅/화면 → 핵심 컴포넌트 → 훅/상태 → 데이터 계층 → UI 토큰/국제화 순으로 분석한다
- 각 단계에서 발견한 이슈/리스크/개선 포인트를 별도 목록으로 기록한다

## 개선 방향
- 유지보수성: 책임 분리와 의존성 최소화, 재사용성 확대
- 안정성: 런타임 오류 가능성 축소, 경계 조건 명확화
- 성능: 렌더링/네트워크 병목 후보 추적
- 테스트성: 단위/통합 테스트의 추가 여지 재확인

## 수정 제안 항목 (단계별 발견 사항 요약)
### Step 0 (기본 설정/도구 체인)
- `tsc -b` 사용 중인데 `tsconfig.*`에 `composite: true`가 없음 → 타입 체크/빌드 실패 가능성 점검 및 필요 시 보완
- `openapi:check`가 `git diff` 전제 → CI/배포 파이프라인에서 git 상태 의존성 확인 필요
- 실제 패키지 매니저 기준 불명확( lockfile 존재 ) → 팀 표준/CI 고정 여부 확인

### Step 1 (라우팅/전역 흐름)
- 인증 상태 판단이 `isSuccess` 기반이라 로딩 중 UX가 비인증처럼 보일 수 있음 → 로딩 상태 표현 분리 검토
- 라우트 에러 메시지 통합은 되어 있으나 상태별 메시지 노출 범위 재확인 필요

### Step 2 (핵심 컴포넌트 구조)
- `HomeFeedThreadList`, `ThreadDetailView`에 상태/액션/뮤테이션/에러가 집중 → 책임 분리 및 계층화 필요
- `ThreadCard/ThreadCardView/EntryList` props 폭증 → 인터페이스 단순화 또는 컨트롤러/프리젠터 분리 검토
- Home/Detail 화면의 Entry 렌더/액션 구조 중복 → 공통화/재사용 구조 정리 필요
- `ThreadCard` 단위 엔트리 fetch → 스레드 수 많을 때 쿼리 폭증 가능, 가시성 최적화 외 추가 제어 검토
- 입력 컴포넌트 간 debounce/submit 패턴 불일치 → 행동 일관성 기준 마련 필요

### Step 3 (훅/상태 전파)
- 컨트롤러 훅이 상태/쿼리/뮤테이션/네비게이션까지 과밀 → 레이어 분리 필요
- URL 상태 동기화(`useHomeFeedUrlState`)가 여러 effect로 분산 → 경계 케이스 리스크, 단일 정책 정리 필요
- draft 저장이 500ms 주기 반복 → 입력 집중 시 localStorage write 부담 가능
- 드래그/포커스 상태 전달 경로가 길고 분산 → 단순화 또는 공통 훅 정리 필요
- 로컬 에러와 글로벌 에러 병행 → UX 기준 통일 필요

### Step 4 (데이터 계층)
- `requestEmpty`는 에러 본문/메시지 파싱 없음 → 에러 메시지 일관성 개선 필요
- `threadCache`의 feed/search 동시 갱신 구조가 데이터 스키마 변화에 취약 → 테스트/검증 필요
- 필터 쿼리스트링 조합 로직이 분산 → 필터 확장 시 중복 증가, 공통 빌더 고려
- `highlightMatches`의 HTML 렌더링은 서버 신뢰 전제 → 신뢰 정책 재확인 필요

### Step 5 (UI 토큰/국제화)
- 테마 대비 기준을 강제하지 않음 → 접근성 대비 검증 필요
- `uiTokens` 사용과 직접 Tailwind 조합이 혼재 → 스타일 정책 일관화 필요
- i18n 설정이 localStorage + settings store에 이중 의존 → 동기화 정책 명확화 필요
