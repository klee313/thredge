# Refactor Criteria

## 작성 규칙 (모든 대상 파일 공통)
각 리팩토링 대상 파일마다 아래 항목을 반드시 기록한다.

- 파일명: ...
- 역할/책임 요약: 이 파일이 “무엇을 해야 하는지”에 대한 현재 계약. 리팩토링 중 가장 자주 잃어버리는 게 책임 경계라서 필수.
- 상태 소유권/전파 경로: 무엇이 여기서 결정되고, 무엇이 외부에 의존하는지. 상태 측면의 리팩토링의 영향 범위를 고려하기 위함. 리팩토링 난이도의 70%는 여기서 결정됨. React라면 특히 필수.
- 의존성/결합도: 이 파일을 바꾸면 같이 깨질 수 있는 것들. 리팩토링 때 같이 고려해야 하는 파일들. 다음 리팩토링 후보로 고려할 것들.
- 리팩토링 목적: 어떤 이슈를 발견했으며, 왜 그것이 이슈인지. 그래서 어떻게 개선하는 것이 목적인지. 에러 처리 / 경계 조건, 성능 병목 해소 등.
- 계약(Contract)과 불변조건(Invariants): 리팩토링 중 “절대 깨면 안 되는 규칙”
- definition of done: 어디까지 하면 멈추는지. 테스트가 없어도 “동작 동일”, “렌더 결과 동일” 같은 문장으로 충분.

## 리팩토링 절차
1. '전체 리팩토링' 지시를 받았다면 코드베이스를 엔트리포인트부터 i18n 등 사소한 부분까지 톱다운으로 읽어보며, 각 파일들에 대해 위 항목을 판단한다. 특정 커밋에 대한 리팩토링 지시를 받았다면, 새로 추가된 파일이나 수정된 파일들을 굵직한 로직 변경에 해당하는 부분부터 톱다운으로 읽어본다.
2. 일반적인 개발 맥락에서 권장되는 코드 작성 원칙에 견줄 때 지금 보는 파일에 문제가 있으면 리팩토링 후보에 올린다. (결합도가 높거나, 숨은 의존성이 많거나, 중복코드가 많거나, 성능 문제가 있거나, ...)
2-2. 사용자 경험을 높여서 유지시간을 늘릴수록 이득이 큰 빅테크 서비스가 아니라 사용자 경험이 조금 떨어져도 확실한 컨텐츠로 승부하는 스타트업 서비스를 개발하는 것이므로, 사용자경험과 서버부하 사이의 가치가 상충될 때는 서버 부하를 줄이는 방향으로 리팩토링을 수행하며 해당 부분은 주석으로 해당 방향으로의 결정 이유를 밝힌다. 다만 온보딩/결제/검색/핵심 소비 플로우 같은 핵심 전환 구간, 고객 문의/이탈이 실제로 발생한 명확한 UX 이슈, SLA/신뢰(오작동 체감)와 직결되는 영역 같은 부분은 UX 우선 가능
3. '리팩토링 후보 파일 목록' 문서를 작성한다.
3-2. 각 항목을 “작업 단위”로 쪼개고 난이도/리스크 태그 달기
4. 3번 문서의 첫 번째 항목부터 리팩토링 작업을 진행하며, 작업이 끝났을 때는 해당 항목에 작업 이력을 업데이트 한다.
